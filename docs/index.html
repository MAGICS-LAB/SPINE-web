Foundation models give robots powerful high-level reasoning, yet turning that intelligence into reliable physical action remains difficult: roboticists must still align device drivers, network interfaces, sensors, controllers, and safety constraints for each platform. This often-overlooked integration layer acts as the robot's spinal cord, translating high-level intent into coordinated physical behavior, and remains a primary bottleneck for scalable Embodied AI. Hence, we propose SPINE (Scalable Physical Integration with ageNtic Expertise), an agentic framework for systematically debugging and deploying bimanual robots for teleoperation. SPINE centers on two subagent-driven workflows: a profile builder that compiles robot-specific context and a debugger that uses that context to iterate through diagnosis, repair, and validation until teleoperation succeeds.

Across two bimanual robot platforms and 12 debugging scenarios, novice-operated SPINE achieved more complete and efficient recovery than human operators using Claude Code. On DOBOT X-Trainer, SPINE improved success from 76% to 100% and reduced mean time-to-teleoperation by 30%; on AgileX PiPER, SPINE also achieved 100% success and reduced mean time-to-teleoperation by 38%. These results show that structured agentic debugging can address a key cyber-physical integration bottleneck in real-world robot deployment.

Method

SPINE runs within Claude Code as two skills on a Python backend. /spine-profile-build constructs robot-specific context, and /spine-debug uses that context to restore teleoperation. The skills define procedures, permitted tools and delegation rules; the backend manages execution, persistent state and validation. The main agent selects interventions, but successful completion requires execution evidence checked by the backend.

  1. Step 1

    Observe

    Run the live teleoperation pipeline and hidden readiness checks; record active failures in a blocker ledger.

  2. Step 2

    Triage

    Four read-only subagents inspect terminal output, software and configuration, hardware, and readiness checks in parallel.

  3. Step 3

    Repair

    Apply one software edit, or guide the operator through one physical action from a hardware playbook.

  4. Step 4

    Verify

    Close only when the pipeline and readiness checks pass in the same cycle; otherwise return to triage.

Profile building

The operator supplies documentation, a known-good repository and setup facts. Nine extraction subagents work in parallel: eight cover robot identity, components, interfaces, software, configuration, procedures, safety and diagnostics, and the ninth reconstructs the teleoperation pipeline.

  • Eight category files and a manifest, exposed as contracts, probes and readiness checks, hardware playbooks, and a command graph of the teleoperation pipeline
  • The operator confirms the command graph, interfaces, playbooks and hidden readiness checks
  • Nine curator subagents and an adjudicator review the profile; a deterministic profile doctor checks it before it is sealed
Debugging

debug start collects live evidence through the declared pipeline and records active failures in a blocker ledger. Four read-only subagents examine terminal evidence, software and configuration deviations, hardware visibility, and readiness-check relevance in parallel.

  • A software repair goes through debug after-fix; one physical action from a hardware playbook goes through debug continue
  • debug finish closes a case only when the live pipeline and hidden readiness checks both pass in the same latest cycle
  • /spine-closeout stores the incident; memory keeps a fix as resolved only with a passing validation record

Debugging Scenarios

Twelve scenarios across software-only (SW), hardware-only (HW) and hybrid (HY) faults. Each contains two faults except D-HW1. An administrator implants them without revealing the scenario; success means the follower arms and grippers respond to the master arms while the required camera streams are available.

Results

Per-scenario outcomes. SPINE runs three trials per scenario; human trials pool seven operators on DOBOT and nine on PiPER. OSS is the fraction of implanted faults resolved in a trial; TTO is mean ± SD time-to-teleoperation, including unsuccessful trials. Human operators use standard Claude Code with Claude Sonnet 5.0, the same underlying model, but without SPINE.

DOBOT X-Trainer

SPINE resolved every implanted fault, raising OSS from 0.76 to 1.00, and cut mean time-to-teleoperation from 14:51 to 10:20 (30%). The success gain came entirely from software-only and hybrid scenarios; both conditions resolved all hardware-only faults. SPINE was faster in six of seven scenarios. On D-HY1 it took longer (14:55 vs. 11:55) but resolved all faults, where human operators averaged 0.64.

AgileX PiPER

Human operators already resolved nearly all faults (OSS 0.99), so SPINE's main advantage was speed: it was faster in every scenario and cut mean time-to-teleoperation from 12:30 to 7:48 (38%). The largest reduction came on P-HW1, disconnected camera and CAN links, from 13:36 to 2:45, about 80%.

Ablation on DOBOT

Removing the robot profile or the hardware playbook lowers fault resolution and lengthens debugging, with the losses concentrated in hardware-only and hybrid scenarios. Each ablated variant has one trial per scenario, so these are preliminary.

  • No profile: faults resolved 1.00 → 0.79; mean time 10:20 → 17:00. Half the faults in D-HW2 and none in D-HY1 resolved.
  • No hardware playbook: faults resolved 1.00 → 0.57; mean time 10:20 → 31:25, about three times longer.
  • Both variants still resolved every software-only scenario; their failures came where physical intervention was needed.
